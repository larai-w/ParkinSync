# S5 記録時間削減の見立て（BEN-001）

**作成:** 2026-08-12 ／ **対象:** PoC成功基準 S5「記録時間削減の見立てが立つ」
**元データ:** `data/gutpacer_synthetic.json`（合成・3日分）
**関連:** `veai-private/governance/poc-gutpacer-parkinsync-ben001.md` §4 ／ BEN-001

---

## 1. 何が削減されるのか（導線）

**いまの導線（連携なし）**

```
家族が GutPacer に入力  →  ParkinSync 側の日次表に、人が目で読んで書き写す
```

**PoC後の導線（care-event-v1 連携）**

```
家族が GutPacer に入力  →  care-event-v1 に変換  →  ParkinSync が取り込む（人の転記なし）
```

削減されるのは**入力そのものではなく、2つ目のシステムへの「転記」**。
家族の入力は1回のままで、そこは減らない。**減るのは、同じ値を2度書く作業**。

## 2. 数えられる削減（合成3日分の実測）

| 指標 | 値 |
|---|---|
| 観測日数 | 3日 |
| 排便イベント / モビコール | 3件 / 2件 |
| GutPacer に入力済みの値 | **13個**（排便 3件×3項目 ＋ 服薬 2件×2項目） |
| care-event-v1 に変換された件数 | 6件 |
| ParkinSync の日次行 | 3行 |
| **手作業なら書き写す値** | **9個**（3行 × Date/Bowel/Movi） |
| **連携後に転記する値** | **0個** |

→ **転記の削減率は 100%（9個 → 0個）**。
3日で9個なので、**30日換算では約90個の転記が不要**になる（同じ入力密度が続く前提）。

さらに、転記には**集計**が挟まる（1日の排便が何回だったかを数えて日次行に落とす）。
連携ではこの集計を `parkinsync_import.import_to_daily` が行うので、**数え間違いの余地も消える**。

## 3. まだ言えないこと（BEN-001「80%削減」との距離）

BEN-001 の仮説は**記録時間の80%削減**だが、本PoCで確認できたのは**転記回数がゼロになること**だけ。
次は成り立たない:

- ❌「転記が100%消えた＝記録時間が80%以上減った」
  → 家族の**入力時間**（GutPacer側）は1秒も減っていない。全体時間に占める転記の割合が分からない限り、
    時間の削減率は出せない。
- ❌ 1値あたり何秒、という係数を仮置きして掛け算すること
  → 根拠のない数字が独り歩きする。**未測定を測定値として扱わない**（週次監査と同じ方針）。

## 4. 時間で言うために必要なこと（次の一手）

| # | やること | 誰 | 備考 |
|---|---|---|---|
| 1 | **転記作業を1回だけストップウォッチで計る** | Owner | 3〜5日分を実際に書き写して所要を記録。1回でよい |
| 2 | GutPacer への入力時間も同様に計る | Owner | 分母（記録全体の時間）を得るため |
| 3 | 1と2から「転記が全体の何%か」を出す | AI | ここまで揃えば時間の削減率が言える |

**1と2は合わせて10分程度**で、これが揃うと S5 は「見立て」から「実測」に変わる。
それまでは、S5 は**転記回数ベースの定性メモ**として扱う（PoCの完了定義上はこれで足りる）。

## 5. 結論（PGB報告用）

- **S5 は満たされた（定性）**。連携によって、ParkinSync への**転記が構造的に不要**になることを、
  合成データ上の実数（9個 → 0個）で示せた。集計の手作業と数え間違いも同時に消える。
- **BEN-001 の「80%削減」はまだ裏づけられていない。** 時間を主張するには §4 の実測が要る。
  この区別を曖昧にしないことを、報告時にも明示する。
